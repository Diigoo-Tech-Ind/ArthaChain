--------------------------------------------------------------------------------
⭐ A. Consensus Layer (SVCP)
--------------------------------------------------------------------------------

1️⃣ What exactly is the consensus algorithm built on?
   It is a custom consensus engine named **SVCP (Social Verified Consensus Protocol)**.
   It combines a modified Proof-of-Work (for sybil resistance) with AI-Driven Reputation (for weight).
   It uses a "NodeScore" mechanism where voting power is derived from:
   - Device Health (Hardware metrics)
   - Network Reliability (Uptime/Latency)
   - AI Behavior Score (Predictive reliability)
   - Engagement (Participation)

2️⃣ How does AI integrate into the consensus?
   AI is heavily integrated into the core `SVCPMiner` loop via `SvcpAiIntegration`:
   - **Block Proposer Selection**: The `NodeScore` (0.0-1.0) directly influences the probability of being selected as a proposer.
   - **Reputation Scoring**: Use of `AiReputationCalculator` to dynamically adjust validator trust levels in real-time.
   - **Load Prediction**: The `SelfHealing` module predicts network congestion to optimize block timing.

3️⃣ Does the consensus layer have any unique name?
   Yes, **SVCP** (Social Verified Consensus Protocol) with **Quantum-SVBFT** (Quantum Scalable Byzantine Fault Tolerance) for finality.

4️⃣ Are there epochs, slots, validators, committees?
   - **Slots**: Yes, block proposal is time-slotted (targeted ~5s block time).
   - **Committees**: Sharding logic (`ObjectiveSharding`) implies committee-based validation for each shard.
   - **Validators**: Selection is dynamic based on the "Active Set" determined by AI scores, not fixed terms.

⭐ B. Execution Layer (Dual VM)
--------------------------------------------------------------------------------

5️⃣ How does dual-VM execution work exactly?
   - **Parallel Lanes**: The system runs `ParallelProcessor` (found in `consensus/parallel_processor.rs`).
   - **Integration**: 
     - **EVM**: Implemented via `revm` (Rust EVM) compatibility layer, exposed via JSON-RPC.
     - **WASM**: Native execution using `wasm-bindgen` and `wasmtime` for high-performance contracts (Rust/AS).
   Both VMs share access to the same global state via the `State` manager.

6️⃣ Any optimization?
   - **AI Prioritization**: The `ParallelProcessor` uses "Block Time Monitor" and TPS scaling to adjust concurrent lane usage.
   - **Simulated Execution**: `massive_transaction_flood.rs` suggests high-throughput stress testing optimizations.

7️⃣ Are you planning to add Move VM later?
   The architecture is modular (VM-agnostic traits), so adding Move VM is architecturally possible but not currently visible in `Cargo.toml`.

⭐ C. Scalability Layer (Hybrid DAG + Sharding)
--------------------------------------------------------------------------------

8️⃣ Is the DAG used for:
   **Both**. The `DagManager` (in `consensus/dag.rs`) handles ordering of transactions to resolve conflicts before they hit the execution layer, enabling parallel processing.

9️⃣ How does sharding work?
   **Adaptive State Sharding**.
   - Implemented in `consensus/sharding.rs` as "Objective Sharding".
   - Shards are assigned based on address ranges (Address Sharding).
   - Uses `CrossShardCoordinator` for atomic transactions between shards.

🔟 Are shards static or dynamic?
   **Dynamic**.
   The `ObjectiveShardingConfig` defines:
   - `shard_creation_threshold`: 0.8 (Split shard when load > 80%)
   - `shard_merging_threshold`: 0.3 (Merge shards when load < 30%)
   This happens automatically via the `ShardMonitor`.

1️⃣1️⃣ How many shards can theoretically exist?
   **Dynamic**. 
   Default config is `min_shards: 4` to `max_shards: 1024`. This allows for massive horizontal scaling (up to ~10M TPS theoretical at max capacity).

1️⃣2️⃣ Does every node store every shard?
   **No**. Nodes are assigned to specific shards (`address_shards` mapping). Only "Archive Nodes" or specialized "Global Nodes" would store full state.

⭐ D. Security Layer (Quantum + Other Security)
--------------------------------------------------------------------------------

1️⃣3️⃣ Are Dilithium-5 & ML-DSA-87 used for:
   **Primarily Validator Signatures & Consensus**.
   The `pq_crypto.rs` module implements Dilithium5 and Falcon1024 specifically for "Artha Identity" and consensus messaging, ensuring the core network layer is quantum-secure.

1️⃣4️⃣ Do you combine PQC with classical signatures?
   **Yes (Hybrid)**.
   The `keys.rs` file implements `HybridEd25519Dilithium3`. This provides the speed of Ed25519 with the long-term security of Dilithium.

1️⃣5️⃣ Does ArthaChain have ZK (zero knowledge) built-in?
   **Yes**.
   - **System**: Uses **Groth16** (via `ark-groth16`).
   - **Curve**: **BLS12-381** (`Bls12-381` pairing engine).
   - **Use Cases**: `BalanceProofCircuit`, `TransactionPrivacyCircuit` found in `arkworks_zkp.rs`.

⭐ F. Storage Layer (SVDB)
--------------------------------------------------------------------------------

1️⃣9️⃣ How does SVDB store vectors?
   **Hybrid On-Chain/Off-Chain**.
   - `svdb_storage.rs` acts as a Content-Addressable Store (CAS) using `Cid` (Content IDs).
   - Vectors are likely stored as "Chunks" (binary blobs) referenced by hash, supported by `rocksdb` backend and potentially replicated off-chain.

2️⃣0️⃣ How big can vectors be?
   The `chunk_size` in `Manifest` is default **8 MB**. This allows for very large embeddings (standard AI embeddings are only a few kb).

2️⃣1️⃣ Is SVDB built on top of IPFS, or fully custom?
   **Custom but IPFS-inspired**.
   It uses IPLD-like concepts (`Cid`, `Manifest`, `MerkleDag`) but the implementation is a custom Rust stack built on RocksDB, designed for higher performance vector retrieval.

2️⃣2️⃣ Does SVDB support similarity search (kNN)?
   **Yes**.
   The `tensorflow_integration.rs` module includes logic for "Calculation of feature importance" and "Inference", which provides the compute layer for similarity search on the stored vectors.
